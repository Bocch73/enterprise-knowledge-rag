# 第 14 步：面试交付

## 1. 本步目标

前 13 步解决了“项目能不能工作”，本步解决“你能不能用证据把它讲清楚”。完成后，你应该能够：

1. 用 30 秒、1 分钟和 3 分钟介绍项目。
2. 在 10 至 15 分钟内稳定演示一条完整业务链路。
3. 解释主要技术选择、替代方案和代价。
4. 用测试与评测数据回答“如何证明它有效”。
5. 如实说明未完成边界，而不是把配置文件说成生产运行经验。

## 2. 新名词

### 电梯陈述

电梯陈述是可以在很短时间内说清楚“为谁解决什么问题、如何解决、结果如何”的项目介绍。它不是把
技术名词快速念一遍，而是先让面试官理解项目价值。

### STAR 方法

STAR 是 Situation、Task、Action、Result 的首字母组合，分别表示背景、任务、行动和结果。它用于把一次
工程经历讲成有因果关系的故事。结果必须有证据；如果没有线上数据，就使用真实测试结果并明确样本边界。

### 技术权衡

技术权衡是选择一个方案时同时说明收益、代价和适用范围。例如模块化单体比微服务更适合单人面试项目，
因为部署和调试简单；代价是不能证明大规模独立扩容经验。

### 证据链

证据链是从需求、设计、实现、测试到结果能够互相对应的一组材料。本项目用需求追踪矩阵、架构决策记录、
自动化测试和评测报告形成证据链。

### 演示降级方案

演示降级方案是外部模型、网络或临时环境故障时仍能展示核心能力的备用路径。它不是伪造成功，而是明确
告诉面试官当前故障，并切换到已经保存的真实报告或免费确定性链路。

### 项目边界

项目边界说明哪些能力已经实现和验证，哪些只完成配置，哪些仍是未来工作。主动说明边界通常比模糊夸大
更能体现工程判断。

## 3. 企业级面试交付流程

### 第一步：从业务问题开始

不要先说框架。先说企业制度与操作手册分散，普通大语言模型无法可靠访问私有资料，而且回答缺少出处。
再说明系统先检索获授权的原文，然后让 DeepSeek 依据原文生成带引用的回答，资料不足时拒答。

### 第二步：只讲三条主线

- 产品主线：登录 → 建知识库 → 上传文档 → 后台处理 → 检索或提问 → 查看引用。
- 技术主线：解析与分块 → 向量和全文索引 → 混合检索与融合 → 受约束生成与引用校验。
- 企业主线：权限与审计 → 测试和评测 → 监控与限流 → 持续交付和回滚。

三条主线可以覆盖项目全貌，又不会陷入逐文件说明。

### 第三步：每个结论都配证据

| 面试结论 | 可展示证据 | 不能扩大成什么说法 |
|---|---|---|
| 端到端功能已实现 | 前端工作台、接口测试、浏览器测试 | 已被真实企业大规模使用 |
| 权限边界已实现 | 资源角色测试、管理员审计接口 | 完成了所有合规认证 |
| 检索链路可评测 | 固定语料、5 个问题、版本化 JSON 报告 | 任何领域准确率都是 100% |
| 工程门禁完整 | 105 个后端测试、12 个前端单元测试、2 个浏览器流程 | GitHub Actions 已经在线运行 |
| 部署设计已完成 | Dockerfile、Compose、发布与回滚手册 | Docker 已在本机或生产环境运行 |

### 第四步：用“选择—原因—代价—演进”回答架构题

例如：我选择 PostgreSQL 与 pgvector，让关系数据、权限、全文检索和向量检索处于同一事务边界，降低
项目早期运维复杂度；代价是超大向量规模下扩展能力不如独立向量数据库；当数据量或查询压力达到明确
阈值后，再通过现有向量提供者接口迁移，而不是一开始就增加分布式复杂度。

### 第五步：现场演示只走已排练路径

演示前运行 [面试前检查脚本](../scripts/verify-interview-delivery.ps1)，再按
[演示脚本](delivery/demo-script.md)操作。不要现场更换依赖版本、上传未知文件或展示密钥。

## 4. 真实结果应该怎样表达

推荐说法：

> 在 3 份虚构制度文档、5 个固定问题的本地基准线上，Top 3 命中率、平均倒数排名和归一化折损累计
> 增益都是 1.000；确定性完整链路的引用准确率、引用召回率和拒答准确率也是 1.000。这个样本很小，
> 证明的是评测流程和当前样本没有回归，不能代表真实企业全量语料的泛化效果。

这里最重要的是主动说出样本大小和结论边界。面试官通常关心你是否理解指标，而不是单独追求漂亮数字。

## 5. 本项目最终验证证据

- 后端：105 个测试通过，分支覆盖率 83.26%，静态检查、格式、类型和迁移漂移检查通过。
- 前端：12 个单元测试和 2 个 Chrome 浏览器流程通过；语句覆盖率 94.33%，分支覆盖率 80%。
- 检索增强生成：5 个固定问题的确定性完整链路质量门禁通过，Top 3 命中率、平均倒数排名和归一化
  折损累计增益均为 1.000。
- 部署资产：16 个部署专项测试和 5 份 YAML 格式检查通过。
- 安全：本地环境文件、模型密钥、真实部署密钥、虚拟环境和依赖目录均被版本控制忽略。

## 6. 当前必须如实说明的边界

1. 评测集只有 3 份虚构文档和 5 个问题，尚未覆盖真实企业长文档与噪声数据。
2. 免费持续集成门禁使用确定性哈希向量和确定性回答，不等同于真实语义模型质量。
3. DeepSeek 已完成一次经授权的小规模真实评测，但外部模型不是每次提交都调用。
4. Docker 与 GitHub Actions 配置已经静态验证，本机没有 Docker，工作流尚未在远程仓库实际执行。
5. 当前单进程缓存和限流不能支持多实例一致性，生产扩展时需要 Redis 等共享组件。
6. 单机 Compose 是生产式部署演练，不是高可用、多地域或灾难恢复证明。

## 7. 练习方法

1. 不看文档讲 30 秒介绍，录音后删除不必要的框架名。
2. 按演示脚本完整走两次，并记录耗时。
3. 随机抽取 10 道综合题，每题先用一句话回答，再展开原因与代价。
4. 故意关闭 DeepSeek 路径，练习如何说明故障并切换确定性报告。
5. 让别人连续追问“为什么”，直到能讲清替代方案和边界。

## 10. 完成标准

- 能在 15 分钟内完成演示并保留至少 5 分钟回答追问。
- 能区分“已实现”“已测试”“已配置”和“已上线”。
- 能解释至少 5 个核心技术选择及其代价。
- 演示失败时能使用保存的真实评测报告，不展示或泄露密钥。
- 面试前检查脚本通过，最终提交不包含本地秘密文件。
