# 分层知识工作台设计

## 1. 为什么要从单页升级

第一版前端的目标是验证完整链路：登录、创建知识库、上传文档和带引用问答。它属于最小可用产品，能够证明
技术链路可行，但把知识组织、文档管理和问答放在同一页面，会在知识库和文档数量增长后迅速变得拥挤。

**最小可用产品**是用最少功能验证核心价值的首个可用版本。它不是劣质版本，而是降低早期试错成本的方法；
验证成功后必须继续补齐信息架构、状态反馈和管理能力。

**信息架构**是把产品中的信息和操作按用户任务分组，并设计清晰的层级、导航和命名。它回答“功能放在哪里、
用户怎样找到、不同页面之间是什么关系”。

## 2. 成熟产品带来的启发

本轮只参考公开的产品结构，不复制界面或代码：

- [RAGFlow 知识库配置](https://ragflow.net/docs/configure_knowledge_base)把数据集创建、配置、文档导入和助手使用分开，强调多个数据集带来的问答灵活性。
- [Dify 知识库说明](https://docs.dify.ai/guides/knowledge-base/retrieval)把知识管理、检索增强生成引擎、应用和运行管理作为不同层级。
- [FastGPT 快速开始](https://doc.fastgpt.io/en/guide/getting-started/quick-start)明确区分对话应用、数据集、工作流和智能代理，形成从简单到复杂的产品层级。
- [AnythingLLM 官方网站](https://anythingllm.com/)使用工作空间组织文档、对话和扩展能力，突出本地与私有数据边界。

这些产品的共同规律是：知识资产管理与知识消费分开；概览负责回答“系统现在有什么”，文档中心负责回答
“资料怎样进入系统”，问答页面负责回答“怎样使用这些知识”。

## 3. 当前四层工作台

| 一级页面 | 用户问题 | 当前真实能力 |
|---|---|---|
| 概览 | 系统里有什么、是否正常 | 知识库数量、跨库文档数量、权限统计、数据库就绪状态、快捷入口和摄取流程 |
| 知识库 | 知识怎样分组 | 多知识库卡片、名称与说明搜索、权限筛选、创建知识库、进入文档管理 |
| 文档中心 | 资料怎样进入检索系统 | 切换知识库、上传 PDF/DOCX/Markdown、查看文档、跟踪解析与索引任务 |
| 问答实验室 | 怎样验证和使用知识 | 切换知识范围、建议问题、流式回答、当前会话记录、来源引用和拒答反馈 |

左侧栏同时保留两种导航：上半部分是全局业务模块，下半部分是具体知识空间。用户既能从任务出发，也能直接
进入某个知识库。

## 4. 数据与界面边界

页面统计来自已有后端接口，不使用写死的演示数字：

1. 登录后读取当前用户可访问的全部知识库。
2. 并行读取各知识库的文档列表，汇总跨库文档数量。
3. 调用后端就绪检查，显示应用与数据库状态。
4. 上传成功后用任务接口轮询处理进度，并更新当前知识库的文档数量。
5. 问答会话只保留在当前页面内；后端当前没有持久化对话历史，所以刷新页面后不会伪装成仍有历史。

**派生数据**是根据原始数据计算出的信息，例如把多个知识库的文档数量相加得到“文档总数”。当前概览使用
派生数据，不额外引入虚假的统计接口。

## 5. 为什么暂时没有放进页面的功能

以下入口没有加入当前导航，因为后端还没有完整支持，加入可点击按钮会形成假功能：

- 可视化工作流编排。
- 模型和向量模型管理。
- 跨团队成员管理界面。
- 持久化多轮对话与会话搜索。
- 成本、令牌和问答趋势报表。
- 文档元数据过滤、标签和批量操作。

后续应按“后端能力、权限规则、自动化测试、前端页面”四项同时完成，而不是先画出无法使用的界面。

## 6. 响应式设计

**响应式设计**表示同一套页面根据屏幕宽度重新排列，而不是把桌面页面机械缩小。当前实现包括：

- 桌面端使用固定侧栏和宽内容区。
- 中等屏幕把统计卡片与知识库卡片减少为两列。
- 手机端把侧栏转换成顶部四项导航，并把卡片、表格和摄取流程改成单列。
- 390 像素视口经过真实 Chrome 验证，没有横向滚动。

## 7. 本步知识小结

1. 最小可用产品用于验证价值，企业化迭代需要继续建立信息架构。
2. 知识资产管理、文档摄取和问答消费属于不同用户任务，适合分层设计。
3. 丰富功能不等于增加假按钮，所有可操作入口应有真实接口和权限规则支撑。
4. 概览可以先使用已有接口的派生数据，规模扩大后再建设专用聚合接口。
5. 桌面和手机布局必须分别验证，不能只依赖浏览器自动缩放。
