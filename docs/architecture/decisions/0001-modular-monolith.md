# ADR-0001：使用模块化单体

- 状态：Accepted
- 日期：2026-08-26
- 决策者：项目开发者

## 背景

项目需要覆盖身份、权限、文档摄取、检索、问答、评测和审计。当前只有一个开发者，业务边界仍在学习和验证阶段，但面试中需要展示清晰架构和企业工程能力。

## 候选方案

1. 单个文件或无模块的简单应用：开始快，但功能增加后难以测试和维护。
2. 模块化单体：整体部署一个后端，内部按业务领域隔离。
3. 微服务：每个领域独立部署和通信。

## 决定

选择模块化单体。身份、知识库、文档、摄取、检索、问答、评测、审计和运行模块拥有明确职责，通过应用服务或公开接口协作。

## 原因

- 一个开发者可以完成端到端闭环。
- 本地调试、事务和测试比微服务简单。
- 仍能通过模块边界展示领域拆分能力。
- 将来可以根据真实扩展需求拆出工作进程、检索或模型网关。

## 后果

积极后果：部署单元少、开发反馈快、跨模块事务简单。

代价：如果不执行模块规则，代码可能退化为强耦合大应用。因此必须限制依赖方向，并建立架构测试。

## 重新评估条件

满足以下任一条件时重新评估拆分服务：

- 某模块需要与接口服务完全不同的扩缩容方式。
- 不同团队需要独立发布节奏。
- 故障隔离或安全边界无法在单体内满足。
- 单次部署和测试时间已经显著影响交付。
