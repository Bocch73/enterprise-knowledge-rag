# ADR-0005：文档摄取采用持久任务记录和异步工作进程

- 状态：Accepted
- 日期：2026-08-26
- 决策者：项目开发者

## 背景

解析大文档、生成大量向量和建立索引可能持续数秒到数分钟。如果全部在上传请求中完成，连接容易超时，用户无法看到进度，失败也难以恢复。

## 候选方案

1. 上传请求内同步执行全部工作。
2. 在接口进程中创建临时后台线程。
3. 数据库保存持久任务，Redis 传递任务消息，Celery 工作进程执行。

## 决定

生产路径采用数据库持久任务 + Redis Broker + Linux Celery Worker。`Broker` 是在任务发送者和执行者之间保存并转发消息的消息代理。

第 6 步的 Windows 本地实现使用同一持久任务表，并由独立、有界的数据库轮询工作命令处理。它使用 PostgreSQL 的 `FOR UPDATE SKIP LOCKED` 并发领取任务，不在上传请求内同步解析。这个过渡方案让用户在暂不安装 Docker 的情况下学习任务状态、幂等、重试和恢复；正式部署前必须把任务通知替换为 Redis 和 Linux Celery。

## 原因

- 接口可以快速返回任务编号。
- 独立工作进程可以重试、限流和横向扩展。
- 数据库任务记录提供进度、失败证据和人工重投能力。
- Redis 和 Celery 生态成熟，参考资料和运维工具丰富。

## 后果

积极后果：长任务不占用接口请求，失败可诊断和恢复。

代价：增加 Redis、工作进程、消息重复和任务对账复杂度；Celery 官方不支持 Windows 原生工作进程。当前数据库轮询命令也会增加数据库查询，缺少成熟队列的持续调度、监控和路由能力，只适合本地学习、小规模演示与自动化测试。

所有任务必须满足幂等性，并使用数据库状态转换防止两个工作进程同时完成同一任务。消息投递不等于任务完成，最终状态以数据库为准。

## 重新评估条件

- 团队采用已有的云任务平台或消息系统。
- Celery 在目标部署环境的维护成本不可接受。
- 工作流需要更强的长期编排、人工审批或跨天恢复能力。
