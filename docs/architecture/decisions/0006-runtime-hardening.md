# ADR-0006：本地加固采用可替换限流与缓存，审计保存在 PostgreSQL

- 状态：Accepted
- 日期：2026-08-28
- 决策者：项目开发者

## 背景

系统已经具备完整问答链路和质量评测，但认证、模型调用等高成本接口仍可能被高频请求耗尽资源；
重复查询会重复计算相同向量；管理操作缺少统一审计；运维人员也无法通过标准指标观察请求、错误、
延迟和任务积压。

当前学习计划暂不安装 Docker 和 Redis，所以需要一种能够在 Windows 本地运行、同时不掩盖正式
生产限制的过渡方案。

## 候选方案

1. 立即要求安装 Redis、Prometheus 和完整监控平台。
2. 只增加日志，不实现限流、缓存和指标。
3. 使用明确接口实现单进程限流与缓存，使用 PostgreSQL 保存审计，并通过 Prometheus 标准格式
   暴露指标；多实例部署时再替换共享状态实现。

## 决定

采用方案 3：

- 限流使用进程内固定时间窗口，认证和模型问答使用更严格的独立策略。
- 缓存只保存“文本到向量”的计算结果，不缓存带权限的检索结果和自然语言回答。
- 缓存使用容量上限、最近最少使用淘汰、过期时间和并发填充锁。
- 登录、注册、知识库创建、成员权限变更、文档上传、版本上传和任务重试写入 PostgreSQL 审计表。
- 指标使用 Prometheus 官方 Python 客户端，并为每个应用实例创建独立指标注册表。
- 指标标签只允许有限的路由模板、方法、状态和提供器名称，不使用用户编号、知识库编号、问题或文件名。
- 指标端点支持独立 Bearer 令牌；生产环境还应通过内部网络、反向代理或双向传输层安全保护。

## 原因

- 本地环境无需新增常驻服务，符合当前安装计划。
- 缓存的是与权限无关的计算结果，不会让其他用户取得知识库内容。
- 审计记录与业务数据一起持久保存，可按用户、操作、对象和时间查询。
- Prometheus 格式是常见监控接口，后续可以直接接入采集与告警平台。
- 抽象边界明确，未来替换 Redis 时不需要重写检索和身份业务代码。

## 后果

积极后果：高成本接口有基本资源保护，重复向量计算减少，关键管理操作可追踪，运行状态可被机器采集。

代价与限制：单进程限流和缓存不能在多个应用实例之间共享；进程重启后状态会丢失；固定时间窗口在
边界处可能允许短时突发；PostgreSQL 审计写入增加一次独立事务；当前只有指标暴露，没有部署
Prometheus 服务和告警规则。

## 生产替换条件

- 运行两个或更多应用实例时，限流和缓存必须迁移到 Redis 或受管共享服务。
- 审计量明显影响业务数据库时，增加分区、归档或独立审计存储。
- 正式部署多进程服务器时，按 Prometheus Python 客户端多进程模式配置共享指标目录。
- 真实告警上线前，通过容量测试确定速率、缓存容量、直方图桶和告警阈值。
