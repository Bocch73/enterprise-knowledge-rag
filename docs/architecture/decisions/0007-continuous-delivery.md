# ADR-0007：质量门禁通过后发布不可变镜像，生产部署保留人工批准

- 状态：Accepted
- 日期：2026-08-29
- 决策者：项目开发者

## 背景

项目已经具有后端、前端、真实 PostgreSQL 集成测试、RAG 质量评测和运行时加固。手工在开发电脑上
运行检查容易遗漏，直接在服务器从源码构建也会导致测试制品和上线制品不一致。当前没有已授权的云
账号或生产服务器，也暂不在本机安装 Docker。

## 候选方案

1. 继续依赖开发者手工执行检查和复制源码。
2. 每次主分支提交通过后直接自动修改生产服务器。
3. 使用可复用 GitHub Actions 质量门禁；版本标签重新执行同一套门禁后构建并发布前后端镜像；
   生产环境通过受保护环境、变更清单和人工批准选择确定版本部署。

## 决定

采用方案 3：

- 拉取请求、主分支推送和手工触发均执行后端、前端、浏览器、数据库迁移、确定性 RAG 评测和镜像构建。
- PostgreSQL 集成测试使用临时 Linux 服务容器和固定 pgvector 版本，不依赖开发电脑。
- 所有外部模型密钥均不进入持续集成；RAG 门禁使用确定性本地生成器。
- 发布仅由符合 `v主版本.次版本.修订版本` 形式的 Git 标签触发。
- 发布镜像包含版本标签、源代码修订号、软件物料清单和构建来源证明。
- GitHub 令牌默认只有读取代码权限，只有发布任务获得软件包写入权限。
- 部署前必须备份、审查迁移、获得批准；部署后必须执行存活、就绪和关键业务冒烟测试。
- 失败时优先回滚应用镜像；数据库迁移只有经过单独审查且确认安全时才执行降级。

## 原因

- 可复用工作流保证拉取请求与发布使用相同质量标准。
- “构建一次、按版本推广”减少环境差异和临时修改。
- 发布制品与自动部署分离，适合当前没有生产目标的阶段，也避免未经授权修改外部系统。
- 数据库迁移和应用发布风险不同，分离迁移任务便于观察失败并阻止应用启动。
- 人工批准让团队在高风险数据库变化和外部模型费用前保留明确决策点。

## 后果

积极后果：每次变更都有一致证据；发布镜像可以追溯到标签和代码修订；数据库、对象文件和密钥不会
打包进镜像；开发者不安装 Docker 也能由 GitHub 执行容器验证。

代价与限制：GitHub Actions 会消耗执行时间；第三方 Actions 与基础镜像仍需持续更新和供应链审查；
当前 Compose 方案只有一个后端实例，尚未解决进程内限流和缓存的共享；没有目标服务器就不能声称已经
完成真实生产发布或回滚演练。

## 生产启用条件

1. 配置受保护的 `production` 环境、批准人和允许部署的标签。
2. 使用组织密钥管理系统，而不是把实际密钥提交为文件。
3. 将镜像引用固定到具体版本或摘要，不使用 `latest`。
4. 在预发布环境完成数据库恢复、迁移、冒烟、监控和回滚演练。
5. 两个以上后端实例前，按 ADR-0006 把限流与缓存迁移到共享服务。
