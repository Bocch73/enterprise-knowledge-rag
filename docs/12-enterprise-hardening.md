# 第 12 步：企业级运行时加固

## 1. 本步目标

前十一步已经让系统具备完整业务链路和质量评测。本步解决另一个企业问题：当接口被频繁调用、
外部模型变慢、管理员误操作或系统出现故障时，团队能否保护资源、追查行为并快速定位原因。

本步交付五类能力：

1. **接口限流**：限制单个客户端在一个时间窗口内的请求次数。
2. **向量缓存**：重复文本不必反复计算相同向量。
3. **审计记录**：关键操作持久写入 PostgreSQL，并且只有管理员可以查询。
4. **Prometheus 指标**：暴露请求、错误、延迟、检索、模型和任务积压指标。
5. **安全响应头与质量门禁**：增加浏览器安全策略，并用自动化测试证明行为。

## 2. 为什么这些能力属于“企业级加固”

一个个人演示系统只要能回答问题就可能算完成；企业系统还必须回答：

- 一个客户端持续调用收费模型时，怎样避免费用或计算资源失控？
- 同一段文本被反复查询时，怎样减少重复计算？
- 谁在什么时间修改了权限、上传了文档或重试了任务？
- 请求变慢时，是数据库检索慢，还是模型供应商慢？
- 监控指标会不会反过来泄露用户、文件名或问题正文？

限流、缓存、审计和可观测性分别处理这些问题。它们不是业务页面上的新按钮，却直接决定系统是否
能够安全、稳定地长期运行。

## 3. 新名词解释

### 3.1 限流与固定时间窗口

**限流**是限制请求频率的保护措施。本项目使用固定时间窗口：把时间划分为长度固定的区间，在每个
区间中计数。例如认证接口默认 60 秒内允许 10 次请求，超过后返回状态码 `429`。

`429 Too Many Requests` 表示请求过多；响应中的 `Retry-After` 告诉客户端至少等待多少秒再重试。
`X-RateLimit-Limit` 和 `X-RateLimit-Remaining` 分别表示当前上限和剩余次数。

固定窗口容易理解，但在两个窗口交界处可能出现短时突发。因此它是当前 Windows 单机开发环境的
过渡实现，多实例生产环境应使用 Redis 等共享存储并评估滑动窗口或令牌桶算法。

### 3.2 生存时间、最近最少使用与缓存击穿

**生存时间**（Time To Live）是缓存项从写入到过期的时间，常简称 TTL。本项目默认 300 秒。

**最近最少使用淘汰**（Least Recently Used）在缓存达到容量上限时，先删除最长时间没有访问的条目，
常简称 LRU。本项目默认最多保存 512 个向量。

**缓存击穿或缓存惊群**是同一个缓存项失效时，许多并发请求同时访问后端计算。当前实现使用并发填充
锁，让同一应用内只有一个请求负责生成该向量，其他请求等待结果。

### 3.3 审计记录

审计记录是面向安全与责任追踪的持久证据，不等同于普通调试日志。它至少保存：发生时间、操作者、
操作类型、资源类型和编号、结果、网络状态码及请求编号。

本项目审计登录、注册、知识库创建、成员权限变更、文档上传、文档新版本和摄取任务重试。删除接口
目前尚未实现，因此不能声称已审计删除；以后实现删除需求时必须同步增加审计事件。

“追加式”表示应用只提供新增和查询，不提供修改或删除审计记录的业务接口。它能阻止普通用户篡改，
但拥有数据库高权限的人员仍可能修改记录。正式环境还应采用独立数据库角色、归档、备份或防篡改存储。

### 3.4 Prometheus、采集与指标类型

**Prometheus** 是一个监控与告警系统。应用通过 `/metrics` 输出标准文本，Prometheus 服务定时访问
这个地址，这个动作叫做**采集**（scrape）。本步只实现指标输出，暂时不安装 Prometheus 服务。

本项目使用三种指标类型：

- **计数器**（Counter）：只增加，例如请求总数、限流拒绝次数和模型调用次数。
- **仪表**（Gauge）：可以增加或减少，例如等待、运行、完成和失败的任务数量。
- **直方图**（Histogram）：把耗时放入多个区间，例如请求、检索和模型调用耗时。监控系统可以据此
  计算第 50 或第 95 百分位延迟。

Python 客户端的 Summary 类型不在客户端计算分位数，所以需要聚合第 95 百分位时选择 Histogram。

外部模型还暴露四组低基数指标：

- `rag_external_model_calls_total`：按操作、提供商、模型和成功/失败结果累计调用；
- `rag_external_model_retries_total`：累计有限重试次数；
- `rag_external_model_call_duration_seconds`：包含重试在内的调用延迟直方图；
- `rag_external_model_estimated_cost_total`：按提供商、模型和币种累计估算费用。

Prometheus 中最近 5 分钟的失败率可用“失败调用速率 ÷ 全部调用速率”计算。调用编号不能作为指标标签，
否则会产生高基数；它只进入内容无关的有界调用账本和评测报告。

### 3.5 高基数标签

指标标签用于按方法、路由、状态或供应商分类。**高基数**表示一个字段可能产生大量不同值，例如用户
编号、知识库编号、文件名和完整问题。如果把它们作为标签，监控系统会创建大量时间序列，增加内存和
存储成本，也可能泄露敏感信息。

本项目只使用受控的路由模板、方法、状态码、策略和供应商名称。带随机编号的真实路径会被转换为固定
模板，未知路径统一记为 `unmatched`。

## 4. 当前架构

```text
客户端请求
   │
   v
请求编号中间件
   │
   v
审计中间件 ───────────────> PostgreSQL audit_events
   │
   v
限流中间件 ──超限──> 429 + Retry-After
   │
   v
业务路由 ──> 检索 / 向量提供器缓存 / DeepSeek
   │                         │
   └────────运行指标─────────┘
                    │
                    v
             GET /metrics
```

中间件是在业务路由前后统一处理请求的软件层。本项目让请求编号位于最外层，因此即使请求被限流拒绝，
错误响应和日志仍然具有同一个请求编号。

## 5. 限流策略

默认配置如下：

| 策略 | 范围 | 60 秒默认上限 | 原因 |
|---|---|---:|---|
| 认证 | 注册、登录 | 10 | 降低暴力猜测密码和批量注册风险 |
| 回答生成 | 普通回答、流式回答 | 20 | 保护收费模型和高成本检索链路 |
| 默认业务 | 其他 `/api/v1` 业务接口 | 120 | 防止异常客户端持续占用资源 |

存活和就绪检查不会被限流，否则监控探针可能因为业务流量而误判应用已死亡。客户端身份优先根据
访问令牌的 SHA-256 摘要区分，匿名请求使用网络地址摘要；原始令牌不会保存到限流表或指标中。

可在 `backend/.env` 中调整：

```dotenv
RAG_RATE_LIMIT_ENABLED=true
RAG_RATE_LIMIT_WINDOW_SECONDS=60
RAG_RATE_LIMIT_DEFAULT_REQUESTS=120
RAG_RATE_LIMIT_AUTH_REQUESTS=10
RAG_RATE_LIMIT_ANSWER_REQUESTS=20
```

这些数字只是本地安全默认值，不是经过生产容量测试得到的服务级别目标。正式阈值必须依据业务峰值、
实例数量、供应商额度和误拒绝成本确定。

## 6. 向量缓存策略

缓存只包裹“文本转换成向量”的提供器接口。缓存键由提供器身份和文本共同计算 SHA-256 摘要；内存中
保存向量副本，读取时再次复制，避免调用方修改缓存内容。

```dotenv
RAG_EMBEDDING_CACHE_ENABLED=true
RAG_EMBEDDING_CACHE_MAX_ENTRIES=512
RAG_EMBEDDING_CACHE_TTL_SECONDS=300
```

本项目有意不缓存带权限的检索结果和自然语言回答。它们与用户权限、知识库版本和问题上下文有关，
如果缓存键遗漏权限版本，Alice 的结果可能被错误返回给 Bob。缓存向量属于与权限无关的纯计算结果，
风险更容易控制。

缓存位于应用进程内，应用重启后会清空，多个实例之间也不共享。它减少重复计算，但绝不能成为唯一
可信数据来源。

## 7. 审计记录与管理员查询

数据库迁移 `20260828_0006_runtime_hardening.py` 创建 `audit_events` 表。每条记录包括：

- 唯一编号和发生时间；
- 操作者用户编号，认证失败时可以为空；
- 操作、资源类型、资源编号和成功或拒绝结果；
- 网络状态码和请求编号；
- 只包含方法和路由模板的受控详情。

审计中间件不读取请求正文，因此密码、访问令牌、问题正文和文档内容不会进入审计详情。审计写入使用
独立数据库事务，业务请求结束后仍可以记录成功或失败结果；写入失败会记录内部错误，但不会把敏感
请求内容输出。

管理员可以在接口交互页面调用：

```text
GET /api/v1/admin/audit-events
```

支持按操作者、操作、资源类型、资源编号和时间范围过滤，并使用 `offset` 与 `limit` 分页。普通用户
访问会被拒绝，`limit` 最大为 200，避免无限查询。

## 8. 运行指标

启动后访问：

```text
GET http://127.0.0.1:8000/metrics
```

主要指标覆盖：

- 网络请求总数、状态与耗时；
- 限流拒绝次数；
- 向量缓存命中和未命中次数；
- 检索耗时；
- 模型调用成功、失败和耗时；
- 各状态摄取任务数量。

本地默认可以直接访问。非本地环境必须设置一个独立、至少 32 个字符的随机监控令牌：

```dotenv
RAG_METRICS_ENABLED=true
RAG_METRICS_BEARER_TOKEN=这里填写单独生成的至少32字符随机值
```

采集端使用 `Authorization: Bearer <监控令牌>`。这个令牌不是用户登录令牌，不应放入浏览器页面、日志
或版本库。生产环境还应让 `/metrics` 只在内部网络可达。

## 9. 管理员摄取队列

管理员可以调用：

```text
GET /api/v1/admin/ingestion-jobs?status=failed&offset=0&limit=50
```

它按创建时间倒序返回任务、状态、失败原因和重试次数，用于发现积压与失败。普通用户只能通过原有资源
权限接口查看自己有权访问的任务，不能借管理员接口枚举全局任务。

## 10. 安全响应头

所有响应新增：

- `Referrer-Policy: no-referrer`：不把当前地址作为来源信息发送给其他站点。
- `Permissions-Policy`：默认关闭摄像头、麦克风和地理位置能力。
- `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`：接口响应默认不加载外部资源，也
  不允许被其他页面嵌入为框架。

这些响应头是纵深防御，不能代替输入校验、服务端授权、加密传输和安全前端配置。

## 13. 当前限制与生产升级条件

1. 限流和缓存是进程内状态；两个以上实例必须替换为 Redis 等共享实现。
2. 多进程服务器必须按 Prometheus Python 客户端的多进程模式配置指标目录与生命周期。
3. 当前只暴露指标，没有安装 Prometheus、Grafana 或告警规则。
4. 当前没有经过并发容量测试，限流阈值和直方图区间需要根据真实流量校准。
5. 审计与业务数据在同一个 PostgreSQL 中；大规模使用时需要分区、归档和独立权限。
6. 审计没有数据库级不可篡改保证；高安全场景需要外部防篡改存储。
7. 还没有完整的分布式请求追踪，当前以请求编号关联网络日志和审计记录。

## 15. 本步知识点总结

1. 限流保护系统和外部模型预算，超限使用 `429` 与 `Retry-After` 明确通知客户端。
2. 固定窗口简单但存在边界突发，进程内状态也不能支撑多实例一致限制。
3. 缓存必须设置过期时间、容量和淘汰策略，并防止并发缓存击穿。
4. 权限相关结果很难安全缓存；当前只缓存文本向量这一纯计算结果。
5. 审计记录服务于安全追责，不能保存密码、令牌、问题正文或完整文档。
6. Prometheus 的计数器、仪表和直方图分别适合累计事件、当前状态和延迟分布。
7. 指标标签必须受控；高基数标签既消耗资源，也可能泄露业务信息。
8. 本地过渡实现必须明确生产替换条件，不能把“能演示”说成“已具备生产集群能力”。
