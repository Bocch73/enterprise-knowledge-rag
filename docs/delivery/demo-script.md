# 10 至 15 分钟项目演示脚本

## 一、演示前一天

1. 确认 PostgreSQL 17 服务正在运行，项目数据库可以连接。
2. 不更新 Python、Node.js、PostgreSQL 或依赖版本。
3. 运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\verify-interview-delivery.ps1
```

4. 用 3 份虚构样本文档完成一次排练，不上传个人或公司真实资料。
5. 确认 `backend/.env.deepseek` 被 Git 忽略，但不要打开它或展示密钥。
6. 保留 [确定性完整链路报告](../../evaluation/reports/reference-deterministic-full-v1.json)和
   [DeepSeek 小规模实验报告](../../evaluation/reports/reference-deepseek-v1.json)作为备用证据。

## 二、启动顺序

### 终端一：后端接口

```powershell
cd E:\codex项目\rag1\backend
.\.venv\Scripts\python.exe -m app.server --reload
```

看到服务启动后，打开 <http://127.0.0.1:8000/api/v1/health/ready>。解释：就绪检查同时验证应用是否
可以接收业务流量，不只是判断进程是否存在。

### 终端二：文档工作进程

```powershell
cd E:\codex项目\rag1\backend
.\.venv\Scripts\python.exe -m app.cli.run_ingestion_worker
```

解释：上传接口快速返回，解析、分块和索引由独立后台工作进程完成，避免长任务占住网络请求。

### 终端三：前端

```powershell
cd E:\codex项目\rag1
powershell -ExecutionPolicy Bypass -File .\scripts\start-frontend.ps1
```

打开 <http://127.0.0.1:5173>。

## 三、现场时间线

### 0:00—1:00：业务问题与方案

建议说：

> 企业制度和手册分散，关键词搜索容易漏掉同义表达，普通大语言模型又不能可靠访问私有资料。我做的
> 系统先在用户有权限的知识库中检索原文，再让 DeepSeek 只依据原文回答并展示引用；没有依据时拒答。

### 1:00—3:00：架构全景

打开[系统架构文档](../architecture/system-architecture.md)，只讲五个边界：Vue 前端、FastAPI 接口、
后台摄取工作进程、PostgreSQL 与 pgvector、DeepSeek 模型提供者。强调当前是模块化单体，不是微服务。

### 3:00—7:00：完整产品链路

1. 登录并创建一个名为“面试演示制度库”的知识库。
2. 上传 `evaluation/fixtures/security-policy.md`。
3. 展示任务先进入等待状态，再由工作进程处理完成。
4. 简要展示文档版本与片段，不展开内部数据库字段。
5. 提问：“员工远程访问公司系统需要满足什么认证要求？”
6. 展示回答“必须使用多因素认证”和对应来源引用。

解释：引用不是模型随意生成的链接。服务端只接受当前检索上下文中的来源标识，并在返回前校验。

### 7:00—9:00：拒答与权限

提问：“公司周五下午茶的预算是多少？”系统应说明当前资料不足。随后解释：拒答是重要质量能力，
因为企业场景宁可承认不知道，也不能编造制度。再指出知识库使用资源级角色控制，检索前即过滤权限，
不是生成回答后才隐藏数据。

### 9:00—11:00：质量证据

打开[确定性评测报告](../../evaluation/reports/reference-deterministic-full-v1.json)，只展示汇总字段。说明：

- 固定语料为 3 份虚构制度文档，共 5 个问题。
- Top 3 命中率、平均倒数排名、归一化折损累计增益均为 1.000。
- 引用准确率、引用召回率和拒答准确率均为 1.000。
- 样本很小，数字证明当前基准线和回归门禁，不代表真实企业全量资料准确率。

### 11:00—13:00：企业工程能力

展示 `.github/workflows/quality-gates.yml` 和 `deploy/compose.production.yml`，解释自动测试、真实 PostgreSQL
服务容器、确定性 RAG 门禁、非根容器、文件型密钥、独立迁移及回滚。明确说这些配置已静态验证，
但因为本机未安装 Docker、仓库未推送远程，不能声称已经在线运行或生产上线。

### 13:00—15:00：总结与邀请追问

> 这个项目的重点不是接通一个聊天接口，而是把文档摄取、权限检索、可验证引用、质量评测和安全交付
> 连成闭环。我可以继续展开混合检索、引用校验、权限模型或发布回滚中的任意一部分。

## 四、故障降级方案

| 故障 | 现场处理 | 可以展示的证据 | 必须说明 |
|---|---|---|---|
| DeepSeek 超时或限额 | 不重复消耗费用，切到本地确定性报告 | 保存的 DeepSeek 和确定性 JSON 报告 | 这是历史真实结果，不是现场调用 |
| 前端启动失败 | 使用接口交互页展示健康、登录、上传与问答 | 后端接口测试和浏览器测试结果 | 前端当前故障，不掩饰 |
| PostgreSQL 未启动 | 不现场重装，展示架构、测试与报告 | 真实数据库集成测试、迁移文件 | 此时不是现场端到端运行 |
| 网络不可用 | 使用全部本地文档和确定性评测 | 版本化评测报告 | 外部模型无法现场调用 |
| 时间不足 | 只演示问答、拒答和评测三段 | 引用页面、拒答页面、报告汇总 | 跳过了哪些环节 |

## 五、现场禁止事项

- 不打开 `.env`、`.env.deepseek` 或部署密钥目录。
- 不粘贴来历不明的真实企业文档。
- 不现场安装 Docker、升级数据库或重建环境。
- 不把确定性生成器称为真实大语言模型。
- 不把配置完成称为已经生产上线。
